# Сборка Windows-движка для Android

Этот инструмент собирает не APK, а внутренний runtime-пакет для RamenWine:
ARM64 Linux/glibc-среду, Box64 для x86-64 Linux-компонентов и Wine 11 WoW64
для 32-битных и 64-битных Windows-программ.

**Важно:** ZIP ниже — формат результата сборки и передачи компонентов внутри
проекта, а не действие игрока. В целевой версии сам RamenWine получает этот
пакет из закреплённого подписанного канала, проверяет его, устанавливает в
собственную закрытую папку и обновляет автоматически. Игрок не ищет ZIP и не
выбирает его через файловый менеджер. Автоматический загрузчик и подписанный
канал пока не реализованы.

## Что будет собрано

1. Минимальная Ubuntu 24.04.5 ARM64 с проверкой контрольной суммы архива.
2. Box64, собранный для ARM64 Linux/glibc, а не для Android/Bionic.
   К нему добавляется проверенный x86-64 набор библиотек из того же
   зафиксированного исходного выпуска Box64; 32-битные Linux-библиотеки
   не включаются, потому что 32-битные Windows-программы работают через WoW64.
3. Wine 11.0 с новым WoW64: x86-64 Linux-загрузчик и Windows-компоненты
   обеих архитектур — 32-битной и 64-битной.
4. Wayland-драйвер Wine: один x86-64 Linux-файл и два Windows-файла
   (x86-64 и i386). Для его сборки устанавливаются Wayland-инструменты
   и библиотека XKB Registry; в гостевую систему также включены файлы раскладок
   клавиатуры XKB, а Wine получает их путь явно. Путь поиска DLL включает
   обе Windows-архитектуры. Каждый новый Wine-префикс создаётся с явно заданным
   `WINEARCH=wow64`, чтобы запускать 32-битные и 64-битные Windows-программы
   через одну 64-битную Linux-среду.
   Box64 получает отдельный путь к своему x86-64 набору Linux-библиотек.
   Перед упаковкой проверяется архитектура каждой поставляемой общей библиотеки
   этого набора, а также целостность и границы всех её символических ссылок.
   Для Wayland/XKB также поставляются ARM64-версии библиотек, на которые
   рассчитаны соответствующие Box64-обёртки; x86-64 версии остаются в rootfs
   для самого Wine и запасного режима эмуляции. Архитектура и зависимости
   обеих групп проверяются до создания ZIP.
   Пакет не пройдёт проверку, если любого из трёх драйверных файлов не будет.
5. Базовые библиотеки Wayland, XKB, EGL, Vulkan и мультимедиа в гостевой
   Linux-среде, а также шрифты DejaVu и Noto CJK.
6. Два небольших Windows Wayland probe-клиента (x86 и x86-64), которые
   собираются MinGW и входят в ZIP для отладочного запуска через тот же Wine.
7. Внутренний ZIP-пакет с SHA-256-манифестом. Его будет автоматически получать и устанавливать RuntimeProvisioner внутри RamenWine; файл не показывается игроку.

Wine собирается с Wayland и без X11. Windows Desktop, Explorer,
Проводник, панель задач и рабочий стол не устанавливаются как оболочка
приложения: RamenWine запускает выбранный EXE напрямую в своей полноэкранной
Android-поверхности.

Это не означает, что нужно урезать Win32/Win64 API до списка известных
движков. Неизвестная или самописная новелла должна проходить через общий
широкий Wine runtime. Минимизировать нужно desktop/build-only содержимое и
необязательные графические add-on пакеты, а не системные реализации Wine,
которые игра может вызывать напрямую или через зависимости.

## Что нужно на компьютере для сборки

Сборщик Android-host проверяет полную цепочку ELF-зависимостей PRoot и
совместимость всех его ELF-бинарников с размером страницы Android 16 КБ:
самого PRoot, загрузчика и каждой поставляемой общей библиотеки. Проверяются
параметры `PT_LOAD` в ELF program headers; файлы, собранные только с
4-КБ выравниванием, отклоняются до упаковки. Файлы собираются во временном соседнем каталоге; готовый
каталог появляется только после успешной проверки и записи происхождения
пакета. При ошибке частичный результат не остаётся в целевой папке.
В `PROVENANCE.json` записываются закреплённый коммит Termux, версии всех
трёх пакетов, версии NDK/SDK и SHA-256 каждого установленного файла PRoot.
Сборщик гостевого runtime сверяет эти значения и сами файлы перед загрузкой
Ubuntu Base. Эти контрольные суммы подтверждают целостность относительно
манифеста, но не являются цифровой подписью издателя.

Обе стадии собираются локально, без GitHub Actions. Нужен Ubuntu 24.04
x86-64, работающий Docker daemon и доступ к `/dev/fuse`, который использует
сборщик Termux. Основной способ — одна команда, которая последовательно
собирает Android/Bionic PRoot, затем Ubuntu ARM64 + Box64 + Wine 11 и
проверяет готовый runtime ZIP:

    python3 tools/build_full_runtime.py \
      --work-dir /путь/к/новому/пустому-каталогу \
      --output /путь/к/ramenwine-runtime.zip

Рабочий каталог должен быть новым или пустым; ZIP должен ещё не существовать
и располагаться вне рабочего каталога. Перед запуском Docker отдельный
сборщик PRoot сверяет закреплённые CLI-ключи, переменные `PROOT_LOADER` и
`PROOT_TMP_DIR`, а также Android-настройки Termux-рецепта. Если исходный
контракт не совпадает с тем, что вызывает Android-приложение, сборка
останавливается до компиляции. Сборщик сохраняет в рабочем каталоге исходники,
кэш и отдельный проверенный PRoot payload — это позволяет разобрать ошибку
и не начинать первую стадию заново. Существующие файлы автоматически не
удаляются и не перезаписываются.

Для раздельной диагностики этапы доступны и по отдельности:

    python3 tools/build_proot_host.py \
      --work-dir /путь/к/новому/каталогу-proot-build \
      --output-dir /путь/к/новому/каталогу-proot-artifact

    python3 tools/build_glibc_runtime.py \
      --proot-host /путь/к/каталогу-proot-artifact/host \
      --work-dir /путь/к/новому/каталогу-runtime-build \
      --output /путь/к/ramenwine-runtime.zip


По умолчанию используется два параллельных задания компилятора, чтобы не
требовать большого объёма памяти. На слабом компьютере сборка может быть
долгой. Параметр --jobs позволяет изменить число заданий. Опция
--no-arm-dynarec отключает ускоритель Box64, если он несовместим с
конкретным ARM64-устройством; это может заметно снизить скорость.

## Проверки, которые выполняются до упаковки

До установки зависимостей компьютера и до скачивания/сборки гостевого
rootfs выполняется полная предварительная проверка Android-версии PRoot,
её загрузчика и всех поставляемых ARM64-библиотек (включая `libtalloc.so.2`
и `libandroid-shmem.so`). Проверяется вся цепочка зависимостей: каждая
библиотека должна входить в `host/lib` либо быть публичной библиотекой
Android NDK, доступной с minSdk 26. Та же проверка повторяется перед
упаковкой итогового runtime ZIP. Затем проверяются оба загрузчика glibc, архитектуры ARM64 Box64
и x86-64 Wine, отдельный Linux-процесс `wineserver`, Linux
`wine-preloader` из `x86_64-unix` и программа `wineboot.exe`, все три
части Wayland-драйвера, библиотеки Wayland/XKB и основные файлы раскладки
клавиатуры XKB. Для `wineserver` и `wine-preloader` отдельно проверяются
архитектура и транзитивные ELF-зависимости.
Дополнительно проверяются обе папки PE-компонентов Wine (`x86_64-windows` и `i386-windows`): в каждой обязателен `ntdll.dll`, а архитектура каждого EXE/DLL/драйвера и других PE-образов должна соответствовать папке.
Для набора библиотек Box64 проверяется не только архитектура каждого `.so`: все найденные библиотеки становятся отдельными точками входа рекурсивной проверки `DT_NEEDED`. Поэтому отсутствующая транзитивная зависимость в библиотеке, которую Box64 загрузит только при обращении игры к конкретному API, обнаруживается до упаковки.
Каталоги PRoot и rootfs также не могут ссылаться за пределы пакета.

Важнее всего проверки ELF-зависимостей: сборщик читает список
динамических библиотек, которые реально запрашивает каждый ELF-файл, и
рекурсивно проходит по цепочке. Для Android/Bionic отдельно проверяются
PRoot и его загрузчик; для гостевого rootfs — ARM64-программы окружения и
Box64, x86-64 Wine и его Wayland-модули, а также x86-64 библиотеки, которые
поставляются вместе с Box64. Для каждой гостевой зависимости
проверяется, что файл найден внутри rootfs и имеет ожидаемую архитектуру; для
PRoot зависимость должна быть в host/lib или в разрешённом наборе публичных
библиотек Android.
Проверка не полагается на системный кэш библиотек, которого ещё нет в
извлечённой Ubuntu Base. Если библиотека или её транзитивная зависимость
отсутствует, имеет неправильную архитектуру либо не найден загрузчик,
упаковка останавливается и показывает имя проблемного файла.

Это предварительная проверка состава и связей файлов, а не выполнение
Wine. Она не доказывает, что Wine успешно создаст префикс или покажет
окно игры на Android. После проверок запускается упаковщик runtime ZIP;
Android-приложение дополнительно проверяет контрольные суммы при установке.

## Чего этот шаг ещё не доказывает

Сборка движка не доказывает, что конкретная Windows-новелла уже работает.
Нужно отдельно проверить Wine на реальном ARM64-телефоне, создать Wine-prefix,
показать тестовое Win32-окно через Wayland, проверить сенсорное управление,
а затем запустить легальную тестовую новеллу. Графическое ускорение DirectX,
мост звука Android и поддержка старых видеоформатов пока не входят в этот
первый пакет.

Успешная проверка файлов не равна успешному запуску игры. APK здесь не
собирается.

## Как этот пакет попадёт на устройство

Сборщик здесь выдаёт проверяемый архив для выпуска. В готовом продукте
пользователь не запускает эти команды и не выбирает результат вручную:
RamenWine получает версионированный пакет автоматически, проверяет подпись
release metadata и SHA-256, распаковывает во временную директорию приложения,
проверяет ELF/PE ABI и зависимости, а затем атомарно активирует его.

До появления полного runtime ZIP, подписанного каталога и Android
RuntimeProvisioner нельзя считать этот процесс реализованным. Наличие
`RuntimePackageInstaller` означает только наличие внутреннего механизма
извлечения/проверки архива; он сам ничего не скачивает и не делает Wine
готовым к запуску.

См. [Runtime Delivery](RUNTIME_DELIVERY.md).
